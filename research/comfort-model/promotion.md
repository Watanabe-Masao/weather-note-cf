# モデルを本番に採用する手順（#47）

新しいモデル、または今のモデルの変更を、アプリで使うまでの手順です。**スコアだけで自動採用はしません。** 判断は人が行い、その根拠を実験の記録に残します。

## 1. 実験の記録を作る
`experiments/<id>.json` を作ります。形は `manifest.ts` の `Manifest` です。必須の項目は次のとおりです。

| 項目 | 中身 |
| --- | --- |
| `modelVersion`・`scaleVersion` | 試すモデルの版（`MODEL_VERSION`）と、評価に使った答えの尺度の版 |
| `commit` | 実験に使ったコードのコミット |
| `dataset` | ID とハッシュ、合成か実データか、**評価の期間**、**評価した件数**、**除外した件数（理由ごと。`quality.ts` の理由）** |
| `seed`・`settings` | 乱数のシード、事前分布・最適化・α の設定 |
| `compared` | 比べたモデル |
| `results` | RPS・対数損失・スキル・較正（同じデータ・同じ期間で、今のモデルと比べる） |
| `checks` | 下の7項目それぞれ：`true`（合格）／`false`（不合格）／当てはまらない理由の文 |
| `decision`・`reason`・`approvedBy` | 採用か見送りか、その理由、承認した人 |

## 2. 7項目を確かめる
1. **mathematical**：確率の合計が1、境目が順に並ぶ、パラメータの制約を満たす（単体テスト）
2. **recovery**：合成データで、取り戻せる条件と取り戻せない条件を区別できる（`synthetic.ts`）
3. **performance**：同じデータセット・同じ評価期間で、今のモデルと比べる。RPS が主、対数損失が補助
4. **calibration**：予測確率と、実際に起きた割合が合っている
5. **stability**：少ない件数・欠損・極端な天気で破綻しない
6. **compatibility**：過去の答え・予測・尺度の版を誤って解釈しない。`MODEL_VERSION` を上げる
7. **contract**：正本（`mathematical-contract.md`）と、その「変更の記録」を更新する

複数の候補から最良のものを選ぶときは、**最終の評価に使うデータを、選ぶのに使ったデータと分けます**（同じデータで選んで評価すると、良く見えすぎるため）。

## 3. PR にする
- モデルのコードの変更、回帰テストの値の書き直し（`UPDATE_GOLDEN=1`）、実験の記録、正本の更新を、1つの PR にまとめます。
- PR の説明に、実験の記録の要点と判断の理由を書き、承認をもらってからマージします。

## テストによる強制
`test/data/model-promotion.test.ts` が、次の2つを確かめます。どちらかが欠けると、CI が失敗します。
- 実験の記録がすべてそろっていること（不合格の項目があるのに「採用」としていないこと）
- アプリが使っているモデルの版（`MODEL_VERSION`）に、「採用」の記録があること

これで、記録なしにモデルの版を上げることはできません。
