# 計算の決まり（新しい仕組み `src/core/`）

肌感・慣れ・判定などの計算を、白紙から組み直すための決まり。いまの式と数字は参考にするだけで、守る対象ではない。新しい仕組みは `src/core/` に作り、できた所から画面をつなぎ替える。いまの計算（`shared/`・`src/beta/`）は、つなぎ替えが済んだ所から消す。

2026-11-15 決定。

## 0. まず二つに分ける：学習なし版と学習あり版

| 版 | 使うもの | 置き場所 | 役目 |
|---|---|---|---|
| **学習なし版** | 材料・推測値・設定だけ。**答え（人の記録）を読まない** | `src/core/plain/` | 記録が1件もなくても答えを出す。学習あり版を比べる物差し |
| **学習あり版** | 学習なし版と同じ材料・推測値に、答えから合わせた数を足す | `src/core/learned/` | その人に合わせる。学習なし版より当たるときだけ使う |

- 材料と推測値は、両方の版で**同じもの**を使う（`src/core/material/`・`src/core/estimate/`）。版ごとに作り直さない
- 学習なし版は、学習あり版と答えを読み込まない（矢印は 学習あり → 学習なし の一方向だけ）。テストで確かめる
- 学習あり版の成績は、いつも学習なし版と並べて出す。勝てない間は学習なし版を出す

## 0b. 「慣れ」は計算式の名前ではない

慣れ（適応状態）は直接は見えない状態で、いくつもの履歴から形づくられると考える。計算式が出すのは、その**もとになる履歴の要約**まで。

| 分け方 | 中身 | 置き場所 |
|---|---|---|
| 環境の履歴 | 長期の気温履歴（`history.long.mean`＝L1、`history.long.ema`＝L2）、短期の履歴（`history.short.ema`＝S、当日の数時間の肌感の重み付き平均。日付をまたいでつなぐ）、肌感の変化の速さ（`feel.rate`） | 学習なし版の推測値 |
| 適応状態 | 履歴から形づくられる見えない状態。置くモデルと、置かずに履歴から直接効かせるモデルを両方作って比べる | 学習あり版の候補 |
| 応答の特性 | 切片（感じ方の中心）・傾き（反応の強さ）・境目・ばらつき | 学習あり版の数（答えから合わせる） |
| 補助の要因 | 時刻と、答えにある日なた・日かげ。活動・服装は材料にないので扱わない（時刻に混ざる） | — |

**関係は3種類に分けて書く**（`docs/core-map.md`）：
- **計算上の依存**：どの値から計算するか。コードだけから作る。線があることは、効くと確かめたという意味ではない
- **仮説上の影響**：何が何に効くと考えているか。`src/core/hypotheses.ts` に id と状態を付けて1か所に書く（手で書く表はこれだけ）。計算上の依存と同じ線を引かない（テストで確かめる）
- **確かめられた関係**：学習あり版を1歩先の予測で比べた結果から作る。効果の大きさと幅を付ける。手で書かない。仮説の状態（仮説 → 確かめ中 → 支持／支持されない）を変えるのはこの結果だけ

## 1. 層は4つ、矢印は一方向

```
材料（material） → 推測値（estimate） → 判定（plain／learned） → 画面（ui）
```

| 層 | 持つもの | してはいけないこと |
|---|---|---|
| 材料 | 記録と予報を**同じ形**にそろえた値。どこから来たか（記録・予報、提供元、速報か）を一緒に持つ | 計算・補い・丸め |
| 推測値 | 材料（とほかの推測値）から計算する値。1つの値に1つのモジュール | データの取得、画面の都合 |
| 判定 | 推測値の名前を並べて作る組み合わせ（7段の確率など） | 推測値を自分で計算し直す |
| 画面 | 判定と推測値を見せる | 計算 |

- `src/core/` の中のファイルは、`src/core/` の外を import しない（例外は `shared/types.ts` の型だけ）。テストで確かめる（`test/data/core-boundary.test.ts`）
- 取得（保存データ・API）は `src/core/` の外。core の関数は、材料を引数で受け取る純粋な関数にする。同じ入力なら必ず同じ答え

## 2. データがないものは扱わない

- 材料の値は「ある（数）」か「ない（null）」の2つだけ。**代わりの値で埋めない**（0℃、予報で穴埋め、日の値で時間の値の代わり、などはしない）
- **「ない」には必ず理由を付ける**。null だけでは、研究のときに原因を追えない。値が null のときは理由があり、理由があるときは値が null（テストで確かめる）

| 層 | 「ない」の理由 |
|---|---|
| 材料 | `notProvided` その出どころに列がない／`unpublished` まだ発表されていない／`blank` 表が理由を言わない空欄（毎時の日照：夜か、まだ出ていないか）／`notObserved` 欠測・値がない／`rejected` 数はあるが品質で外した（資料不足値・品質記号なし） |
| 推測値 | `missingInput` 入力が足りない（どの入力が、どの理由で）／`outOfDomain` 式が使える範囲の外（どの値が、どの範囲を）／`tooShort` 前の日からの並びが足りない（何がいくつあって、いくつ要るか） |
| 並び | `noRow` その日の行が来ていない（取得の失敗・読み込み前）。抜かさずに置くので、位置が何日前かを表す |

- 取得の失敗は core の外のこと。core には「行が来ない」として届く
- 入力が1つでも「ない」なら、その推測値も「ない」（理由は `missingInput`）。画面は「—」を出す
- 代わりの材料を使いたいときは、それを**別の推測値として名前を付けて**作る（例：「日照から推測した日射」）。黙って差し替えない

## 3. 材料にするのは、記録と予報の両方にあるものだけ

| 材料 | 毎時 | 日 | 単位 |
|---|---|---|---|
| 気温 | ○ | ○（平均・最高・最低） | ℃ |
| 湿度 | ○ | ○（平均） | % |
| 風速 | ○ | ○（平均・最大） | m/s |
| 最大瞬間風速 | — | ○ | m/s |
| 降水量 | ○ | ○ | mm |
| 日照時間 | ○ | ○ | 時間 |
| 気圧（海面） | ○ | ○ | hPa |

行に書かれていない場所の事実（風速計の高さなど）は、`Site` として材料と一緒に渡す。予報の風は 10 m（Open-Meteo の `wind_speed_10m`）。記録の風速計の高さが分からなければ「ない」（`notProvided`）。

材料にしないもの（理由）：
- 日射：記録は測っている地点だけ → 日照などからの**推測値**にする
- 露点：予報にない → 気温と湿度からの推測値にする
- 天気の文字・天気コード：記録と予報で形が違う → 表示だけ
- 降水確率：記録にない → 表示だけ
- 毎時の最大瞬間風速：記録（毎時の表）にない

## 4. 品質の扱い

気象庁の品質記号で、材料に入れるかを決める。

| 気象庁 | 材料 |
|---|---|
| 正常値 | 入れる |
| 準正常値（`)`） | 入れる。`rough` に名前を残す |
| 資料不足値（`]`） | 入れない（`rejected`） |
| 現象なし（`--`、降水・日照） | 0 として入れる（測って 0 だった） |
| 欠測 | 入れない（`notObserved`） |
| 未発表 | 入れない（`unpublished`）。**数があっても未発表が先**（出どころが「まだ出ていない」と言う値は、まだ値ではない） |
| 毎時の日照の空欄 | 入れない（`blank`） |

判定の順：列がない（`notProvided`）→ 未発表（`unpublished`）→ 数はあるが品質で外す（`rejected`）→ 表が理由を言わない空欄（`blank`）→ それ以外（`notObserved`）。

気象庁の毎時の表は、日照の欄を**夜（測らない）とまだ出ていない時の両方で空欄**にし、どちらかを書かない（欠測は × や /// と書く）。材料は時計で夜を決めず `blank` のままにする。夜かどうか、「夜は日照 0」とするかは、太陽の高さを知る推測値の役目。いまは `rad.sunshine`（日照から推測した日射）がこれを受け持つ：その時間に太陽が日照の基準（直達 120 W/m²）を超えうる瞬間がなければ、日照は要らない（空欄でも何の理由でも構わない）。超えうるのに日照がなければ「ない」。

## 5. 推測値：計算式とパラメータを分ける

推測値は「計算式」と「パラメータ（式の中で使う数）」の2つに分けて持つ。**計算式の中に数を直接書かない**（マジックナンバーを置かない）。

```ts
// 計算式（src/core/estimate/feel-shade/formula.ts）：形だけ。数は名前で受け取る
export const feelShade = defineFormula({
  id: "feel.shade",                             // 名前。課題・研究メモでもこの名前で呼ぶ
  version: 1,                                   // 式の形を変えたら上げる
  label: "肌感（日かげ）", unit: "℃",
  needs: ["temp", "humidity", "windPerson"],    // 材料か、ほかの推測値
  params: ["neutral", "a0", "a1", "a2", "c0", "c1", "d"],  // 使う数の名前
  domain: { humidity: { min: HUMIDITY_MIN, max: HUMIDITY_MAX }, windPerson: { min: 0 } },
  compute: (x, p) => …,                         // needs がそろい、範囲の中のときだけ呼ばれる
});

// パラメータ（params.ts）：数と、その単位と根拠
export const FEEL_SHADE_MISSENARD = defineParams(feelShade, {
  id: "missenard",
  version: 1,                                   // 数を変えたら上げる
  values: { a2: { value: 0.75, unit: "", basis: "改良ミスナール式の係数：風速のべき" }, … },
});

// 学習なし版（src/core/plain/feelShade.ts）：材料 → wind.person → feel.shade
shadeFeel(hour, { anemometerHeight: 10 }, { windPerson: windPersonSettings(alpha) });
```

- **計算式に書いてよい数は 0 と 1 だけ**。それ以外の数は、名前・単位・根拠を付けて `params.ts`（パラメータ）か `constants.ts`（物理の定数・気象庁の決まりなど、変えない数）に置く。テストで確かめる（`test/data/core-boundary.test.ts`）
- 1つの計算式に、パラメータの組をいくつも持てる。結果には「式の id と版」と「パラメータの組の id と版」の両方を残す
- 結果は「値」か「ない（理由）」のどちらか（2）。`compute` の中で「ない」を作らない。足りない入力と範囲の外は、呼ぶ前に仕組みが見分ける
- 「ない」の理由は、もとの材料まで届ける。推測値を入力にした推測値は、どの入力のどの入力かを点でつないで残す（`windPerson.wind: notObserved`、範囲の外なら `windPerson.windHeight`）
- 結果の `trace` に、通った計算式とパラメータの組（id と版）と、使った数を順に残す。設定から作った組は、id と版が同じでも数が違うので、数も残す
- 依存は `needs` だけ。関数の中でほかの値を取りに行かない
- 同じ値でも式の形が違うもの（慣れの式が3つ、など）は、別の id の計算式にする（`history.long.mean30`、`history.long.ema` など）。数が違うだけなら、同じ式の別のパラメータの組にする
- いつも要るとは限らない入力は `optional` にし、ほかの入力しだいで要るときを `required` に書く（例：日照は太陽が出うる時間だけ要る）。要らないときは `compute` に null で渡り、要るのにないときは `missingInput`
- 前の日からの並び（慣れなど）は `series` で受け取る（新しい日が先）。足りるかどうかは計算式の `enough` が数（パラメータ）で決め、足りなければ `tooShort`。`compute` は足りるときだけ呼ばれる
- **古い版の計算式は消さない**。式の形を変えたら新しい版を足し、古い版は残す（どの記録も、どの版でも計算し直せるように）
- 依存の図は、コードから作る（`src/core/map.ts` → `docs/core-map.md`、`npm run core-map`）。計算式を足したのに図に入っていない、図が古い、ありもしない入力を使っている、循環している、はテストが知らせる

### 学習なし版と学習あり版の違いは、パラメータの出どころ
| 版 | パラメータ |
|---|---|
| 学習なし版 | 根拠を書いた組（文献・気象庁・設定）。答えを読まない。**答えの成績を見て数を直したら、それは学習あり版の組**として扱う |
| 学習あり版 | 同じ計算式に、答えから合わせた組。合わせ方も版を持つ |

## 6. 記録（答え）に保存するもの

- 保存するのは**材料と答えだけ**。肌感・基準・差などの推測値は保存しない
- 推測値は、いつでもいまの式で計算し直す。式を変えたら、全部の記録が新しい式で読み直される
- これまでの記録は、材料と答えだけを引き継ぐ。足りない材料は気象庁の記録から取り直す
- **答えたときに使えた材料（予報か記録か、いつ取ったか）を残す**。1歩先の予測の比べ方（7）では「答えたときの材料で出した予測」と「後の記録で出し直した予測」を分ける。材料なので、この決まりの範囲に入る

## 7. 組み替えと比べ方

- 判定は「どの推測値を、どう組み合わせるか」の宣言にする。学習なし版と学習あり版の両方にある
- 判定の数（境目など）も計算式から分けたパラメータにする。学習なし版は設定か根拠を書いた組、答えから合わせた組は学習あり版にだけ置く
- 比べるときは、同じ材料と同じ答えに、別の組み合わせを流すだけ。成績の決まりは #117
- **1つずつ差し替えて比べる**（`src/core/compare/`）。差を調べたいもの以外は、同じ計算式・同じ組に固定する。例：慣れの影響は、L1 と L2 だけを差し替え、境目のずれ（`judge.shift.season`）と7段の判定（`judge.level7`）は両方で同じものを使う。差し替えられる入力は計算式の `choices` に書き、図にも出る
- 比べられない日（どちらかが「ない」）も結果に残し、理由ごとの件数を出す。数えるのは両方がある日だけ
- **学習に使った答えで成績を測らない**。時間の順に、その答えより前の答えだけで学び、その答えを予測して比べる（1歩先の予測）。学習あり版の勝ち負けは、この成績だけで決める
- 仕組みは `src/core/evaluate/prequential.ts`：答えを時間の順に並べ、1件ごとに、それより**前に**答えたものだけで学び（同じ時刻のものも見ない）、7段それぞれの確からしさを出して点を付ける。点は RPS（段の順を考えた外れ、0 が最良）と当たり。2つの差は同じ答えの上で、日を単位にしたブートストラップの幅つき（種は固定、同じ答えなら同じ幅）
- 予測の形（`Predictor`）は1つ。学習なし版（`plain.level7`：判定の段に全部の重み）は答えを受け取らない。学習あり版は `src/core/learned/` に置き、入口も別（`src/core/learned/index.ts`）。いちばん素朴な学習あり版は答えの割合だけ（`learned.climatology`）：天気から何かを学んだと言えるのは、これに勝ったときだけ
- 順序モデル（`src/core/learned/ordinal.ts`）：P(段 ≤ k) = σ((b_k + ずれ + δ − 肌感) / s)。b_k は設定の境目、ずれは学習なし版の季節のずれ。`learned.ordinal.base` は δ = a₀（境目をまとめて動かす）と広がり s だけを学ぶ。`learned.ordinal.s1` は δ = a₀ + a₁·(肌感 − S)（短期の履歴で切片だけを動かす、S1）。**短期の履歴が効くと言えるのは、S1 が base に勝ったとき**（学習なし版に勝つだけでは足りない）。事前の数と合わせ方の数は `learned/params.ts`（仮、#117 で感度を見る）
- 答え1件の入力は `src/core/plain/caseInputs.ts` が材料だけから作る（答えた場所の肌感・ずれ・S・速さ・学習なし版の段）。半々は肌感を1つに決めないので、その答えは予測に使わない
- 答えを見てパラメータや式を選んだら（学習なし版の数を直した、など）、成績はその日より後の答えだけで測る。選ぶのに使った答えと、成績を測る答えを分ける
- 判定を採用する・版を上げるのは承認してから（D10）

### モデルを見る画面（Model Explorer）を作るとき
- 見せるのは core に移ったものだけ。構造は計算式から、値は同じ `evaluate` で計算して取る。画面の側に式や依存を書かない
- 旧実装（`shared/`・`src/beta/`）を読む仕組みは作らない（別に書き出すと二重管理になる）。旧実装は「未移行」とだけ示し、見たいものは先に core へ移す
- 最初の比べ板：設定 →「慣れの計算を比べる（テスト）」（`src/ui/HistoryCompareBoard.tsx`）。その地点の記録で `compareLongHistory` を動かし、L1・L2・境目の差・選んだ日の段を出す。画面は値を計算しない
- S0 の観察板：設定 →「短期の履歴と答え（テスト）」（`src/ui/ShortHistoryBoard.tsx`）。その日の肌感・短期の履歴 S・変化の速さを `shortHistories` で出し、自分の答えを同じ時間の軸に並べる。表は答えたときの場所（日なた・日かげ）の値。「いつもと違う動き」（昼に冷えた・夜に暖まった時間）で、時刻と履歴を切り分けられる日を探す

## 8. 設計の原則との対応

| 原則 | この仕組みでの形 |
|---|---|
| SRP（単一責任） | 1つの推測値に1つの計算式。計算式は形だけ、数はパラメータが持つ（5） |
| OCP（開放閉鎖） | 新しい式は新しい id で足す。使っている式は書き換えない（変えるなら version を上げる） |
| LSP（置換可能性） | 同じ値の候補は同じ入出力の形にして、判定の側で差し替えられるようにする。パラメータの組も同じ式のまま差し替えられる |
| ISP（インターフェース分離） | 学習なし版と学習あり版、計算と表示で、必要な形を分ける（0・1） |
| DIP（依存性逆転） | core はデータの取り方も画面も知らない。材料は引数で受け取る（1、テストで確認） |
| DRY | 数・単位・根拠の正本はパラメータと定数のファイルだけ、依存の正本は計算式の `needs` だけ。別の登録表や手書きの地図を正本にしない。図はコードから作る |
| KISS | 汎用の実行エンジンは作らない。`needs` がそろえば計算するだけ |

## 9. ライブラリ

増やすのは、決まりを確かめるのに手で書くより確かなときだけ。

| ライブラリ | 使う所 | 入れる時 |
|---|---|---|
| fast-check | 推測値と判定の性質を、多数の入力で確かめる（入力がなければ答えもない、範囲、確率の合計が1、学習なし版は答えを変えても結果が同じ） | 入れた（4.10.2） |
| Zod | 外から来るものの入口だけ（保存されている答えの記録、D1 から戻るデータ）。core の中は TypeScript の型で足りる | 古い記録を引き継ぐ段 |
| Mermaid | 依存の図を `needs` から作って文書に出す（いまの文書と同じ） | 推測値の段 |
| rolldown（`parseAst`） | コードの決まりの検査（数の検査など）を、文字の検索でなく構文で読む。ビルドがすでに使っている解析器なので、新しく増えない（TypeScript 7 には JS から使える解析器がない） | 入れた |

コードの決まりを確かめるテストは、**文字の検索でなく構文で読む**（コメント・文字列・テンプレートを取り違えないため）。

入れないもの：ESLint（数の検査は上の解析器で足りる）、Madge（core の境目は 1 のテストで確かめている）、React Flow・ELK.js（画面でモデルを探す必要が出るまで）。

## 10. この文書の直し方

決まりを変えるときは、同じ PR でこの文書を直す。レビューで見つかった決まりの破れは、ほかの所にもないか横に確かめてから直す。
