# βモデルの数学的正本（MATH-01〜08）

この文書が、βモデル（ちょうどよい温度と範囲）の**数学的な正本**です。コードはこの文書の実装です。計算の本体は `src/beta/engine/` にあり、この文書の項目ごとにファイルを分けています（`drivers.ts`＝MATH-03、`model.ts`＝MATH-04、`estimation.ts`・`ensemble.ts`・`prediction.ts`＝MATH-05、`observations.ts`＝MATH-02 の判定を使って学習用の記録を作る、`learning.ts`＝MATH-07、`evaluation.ts`＝MATH-08）。コードのコメントは、ここの ID（`MATH-04` など）で参照します。README 8章はこの文書の要約です。

各項目に、次のことを書きます。

- 定義
- 単位・尺度
- 成立条件
- 仮定
- 計算方法
- 欠損時の扱い
- 検証
- 実装

「数学的に定義されている」ことと「統計的に検証されている」ことは別です。状態の欄で分けて書きます。

- **定義済み**：数式と意味が決まっている
- **実装済み**：コードとテストがある
- **検証待ち**：合成データや実データで、成り立つかを確かめていない（#35）

変更は、末尾の「変更の記録」に、次の3つのどれかとして記録します。

- 数式の変更
- データの意味の変更
- 実装の最適化

前後の記録が比べられるかどうかを判断するためです。

## MATH-01 観測対象と回答尺度

**定義**：回答 Y ∈ {−3, −2, −1, 0, +1, +2, +3} は**温冷感**（寒い側か暑い側か）です。**快適性**（その状態が快適か）とは別の概念として扱います（決定 D1）。

| Y | 言葉（尺度の版 3） |
| --- | --- |
| −3 | 極寒 |
| −2 | 寒い |
| −1 | 涼しい |
| 0 | ちょうどよい（温冷感の中立。「快適」とは同一視しない） |
| +1 | 暖かい |
| +2 | 暑い |
| +3 | 猛暑 |

- **尺度**：順序尺度です。段の間が等間隔だとは仮定しません（MATH-04 の境目は、段ごとに位置が決まる）。
- **尺度の版**（`scaleVersion`）：数値は同じでも、言葉が違えば別の問いです。
  - 1：寒い・涼しい・やや涼しい・どちらでもない／適温・やや暖かい・暖かい・暑い
  - 2：極寒〜猛暑で、0 が「快適」
  - 3：0 が「ちょうどよい」
  - 版をまたいで集計するときは、版を説明変数として入れるか、版ごとに分けます。
- **快適性**：今は尋ねていません。尋ねるときは、別の変数（例：`comfort ∈ {快適, 不快}`）として、Y とは別に記録します。
- **実装**：`src/beta/reports.ts`（`SENSATIONS`、`SCALE_VERSION`）、`shared/feel.ts`（`LEVELS`）
- **状態**：定義済み・実装済み

## MATH-02 気象データ

**3種類の値を区別します。**

| 種類 | 例 | 記録するもの |
| --- | --- | --- |
| 原観測値 | 気温、湿度、風速、日射 | 値、観測した時刻（`date`・`hour`、10分値なら `minute`）、出どころ（`from`：jma-fixed・jma・amedas・forecast）、取得した時刻（`retrievedAt`） |
| 派生値 | 日なた温度・日かげ温度、移動平均、基準との差 | 値と計算方式の版（`transform`）。元の原観測値も同じ記録に残す |
| モデル推定値 | μ、確率、区間 | 予測の版（`comfort.version`）と、学習の段階 |

- **状態（status）**：出どころから決めます：確定（jma-fixed）／観測（jma・amedas）／予報（forecast）／なし。
- **品質の印（flags）**
  - `temp-forecast`：気温が予報の値
  - `stale`：観測が記録より120分を超えて前
  - `future`：観測の時刻が記録より後
  - `humidity-missing`・`wind-missing`・`solar-missing`：その値がない
  - `solar-lent`：日射を予報から借りた（AMeDAS には日射がないため、普通のこと）
  - `mixed-sources`：観測と予報が混ざっている
  - `no-baseline`・`no-history`：最近の基準や、その履歴がない
- **学習に使う条件**：気温が観測（確定または観測）であり、観測が記録の120分以内で、最近の基準の履歴があり、日なた温度か日かげ温度が計算できること。満たさない記録も保存し、画面と CSV に理由を出します（`train_excluded_reason`）。
- **答えた時刻の値**：気温・湿度・風速は、答えた時刻より前で最も新しい観測を使います。その日の AMeDAS の10分値が正時の値より新しければ（正時の値が予報なら、1時間以内の10分値でも）、それを使い、記録の時刻はその観測の時計で持ちます（0:50 は前日の24時・50分）（12時15分の答え → 12時10分の値。以前は12時の値で、正時の間に気温が動く日は最大で1時間ぶんずれていた）。日射・予報の天気・その日の積算は正時の値のままです（AMeDAS に日射がないため）。古さ（`lagMin`）も、使った観測の時刻から測ります。`minute` のない記録は、正時の値を使った記録です。
- **不変性**：記録に残したスナップショットは、後で気象データが確定値に置き換わっても書き換えません（MATH-06）。
- **実装**：`src/beta/quality.ts`（`inputQuality`、`MAX_LAG_MIN`）、`src/beta/reports.ts`（`snapshotOf`）、正本管理 `src/data/authority.ts`
- **状態**：定義済み・実装済み。120分という境目は暫定です。

## MATH-03 環境指標

**定義**：体感指標 E = f(T, H, W, R; φ) は、気象情報から作った**説明の指標**です。体で直接測った真の体感温度ではありません。

- 日かげ温度：Steadman の体感温度 AT(T, H, W₁.₅)。W₁.₅ は、観測所の風を人の高さ（1.5m）に、周りの様子 φ（べき指数 α）で換算したもの。
- 日なた温度：日かげ温度に、日射による上乗せ sunWarming(R, W₁₀, 吸収率) を足したもの。
- 版：`FEEL_TRANSFORM = "feel-1"`

**二重補正の対応表**（体感指標に入っているものを、個人モデルで重ねて数えないため）：

| 変数 | 体感指標 E に含むか | 個人モデルでの扱い | 注意 |
| --- | --- | --- | --- |
| 気温 | 含む | 基本の入力（E として） | 基準の物差し |
| 今の湿度 | 含む（AT） | 範囲の幅 h の要因（hNow）。中心 μ には入れない | 中心への効果は E で済んでいる。幅への効果だけを検証の対象にする |
| 前日・1週間の湿度 | 含まない | 中心の要因（h1・h7） | 時間をおいた効果 |
| 風速（観測所） | 含む（人の高さに換算） | 感じた風（強い・弱い・なし）による E′ のずれだけを推定する（wS・wN） | 観測所の風と、その場の風の**差**だけを個人モデルで扱う |
| 日射（今） | 日なた温度に含む | いる場所（日なた・日かげ・半々）で選ぶだけ。夜は聞かず日かげ温度 | 観測所と、その場の差 |
| 空の様子（晴れ、答え） | 含まない | 中心と幅の要因（sky）。**日中だけ**（comfort-5）、夜は 0 | 夜の晴れは放射冷却で向きが逆。夜の冷えは日かげ温度（E）に入っている |
| 日中の日射の余熱 | 含まない | 夜の E′ の要因（radNight、×風）。直前の昼の日射の合計が、日の入りからの時間で薄れる（comfort-6） | 地面にたまった熱。0時をまたいでも前の昼の分を使う |
| 前夜の冷え込み | 含まない | 昼の E′ の要因（coldNight、×風） | |
| 最近の基準・季節の向き | 含まない | 中心の要因（慣れ、MATH-05） | 時間に依存する |
| 服装・活動量 | 含まない | 観測していない | 交絡になり得る（#37） |

**欠損時の扱い**：欠けた入力を、典型的な値（中心化して0）として扱うことは**しません**。

- 説明変数の値が欠けているとき（`value(x) = null`）、その変数を使うモデルは、その時点の予測に参加しません。残りのモデルで重みを付け直します（`weightsAt`）。M0 は E だけで動くので、必ず残ります。
- 学習でも、各モデルは、自分の入力がそろった記録だけで推定します。
- 「その時点では当てはまらない」値は 0 で、欠損ではありません（例：昼間の夜の余熱、夜の晴れ）。
- **夜の余熱**（comfort-6、#86）：radNight ＝ ((R − 10) / 5) · e^(−t/τ)。R は直前の昼の日射の合計（MJ/m²：日の入り後はその日の合計、日の出前は前日の合計）、t は日の入りからの時間、τ = RAD_TAU_H。**今は τ = ∞（薄れさせない）**：合成データ（`stored-heat-results.md`、M5、各40人）で、本当の薄れ方（2・4・8時間・薄れない）が分からないまま決めた τ が外れたときの損（RPS）は、薄れない 0.0003（夜 0.0007）、8時間 0.0005（0.0009）、4時間 0.0011（0.0021）、2時間 0.0015。4時間は、一晩中余熱が残る人では comfort-5 と同じだけ悪くなります。薄れる形は式に残し、実データで τ を比べ直します（#54）。comfort-5 までは「その日の朝からの累計」を夜じゅう薄れさせずに使っており、日付が変わった1時以降は新しい日の累計（ほぼ 0）になっていました（0:59 に晴れた日の余熱いっぱい、1:00 にまったくなし、という段差）。余熱 × 風（radNightWind）も同じ薄れた値を使います。昼の暑さは気温そのもの（日射より遅れて上がる）とひなた温度に入っているので、この項は**夜だけ**です（昼に足すと二重に数える）。
- **昼と夜**（comfort-5、#86）：夜は**その場面の日の入りから日の出まで**です。日の出・日の入りは、記録に保存したもの（その日の観測所の値）を使い、ないとき（保存する前の記録、取得できなかったとき）は観測所の位置から計算します（`shared/sunTimes.ts`、公表値と数分以内）。comfort-4 までは時計で 18〜5時（冬の17時台を昼、夏の18時台を夜とみなしていた）。夜の余熱・前夜の冷え込み・晴れの切り替えはすべてこれに従います。
- 体感指標 E 自体が計算できない記録は、学習に使いません（MATH-02）。

- **実装**：`shared/feel.ts`（`feelOf`、`FEEL_TRANSFORM`）、`src/beta/engine/drivers.ts`（`DRIVERS`）、`model.ts`（`missingDrivers`、`usable`）、`ensemble.ts`（`weightsAt`）
- **状態**：定義済み・実装済み

## MATH-04 7段階の確率モデル

**順序ロジスティックモデル**（位置と尺度のモデル）：

```
境目：c = (−h−2g, −h−g, −h, +h, +h+g, +h+2g)
P(Y ≤ k │ x, θ) = σ((c_k − (E′ − μ)) / s)   （k = −3…+2。P(Y ≤ +3) = 1）
P(Y = k) = P(Y ≤ k) − P(Y ≤ k−1)
μ = m₀ + Σ b_j x_j，  h = exp(l₀ + Σ c_j x_j)，  g = exp(q₀)，  s = exp(r₀)
E′ = E + Σ e_j x_j + w_S·[強い風] + w_N·[風なし]
```

- **識別**：位置と尺度は、観測された E（℃）で固定されます。潜在変数の尺度を自由にしないので、普通の順序ロジットにある「位置と尺度の不定性」は、E の係数を1に固定することで解いています。ただし、h・g・s が同時に識別できるかは、データの散らばり方によります（片側の答えだけ、狭い温度だけ、では識別できない。MATH-07）。
- **仮定**：境目は中心について対称で、外の段の幅は g で共通です。この仮定を緩めるのは、データで必要と分かってからにします。
- **モデルの一覧**：M0〜M9（README 8章の表）。どれも同じ形で、x の選び方だけが違います。
- **実装**：`src/beta/engine/model.ts`（`stateOf`、`placeTemp`、`probabilities`、`MODELS`）
- **検証（#35）**：合成データで、μ・慣れの傾き・h・s を取り戻せること（95%区間の被覆率 91〜100%）と、識別できない条件（片側の答え・狭い温度・1日に集中）を「情報不足」にできることを確かめました。2つの入力が一緒に動くときは、推定の相関（|r| ≥ 0.9）で「分けられない組」として検出し、根拠の画面に出します（`confoundedPairs`）。両側で段の幅が違う人では、μ に 0.5℃前後の偏りが残ります（形の仮定の限界。#37 の候補）。
- **状態**：定義済み・実装済み・合成データで検証済み（実データでの検証は今後）

## MATH-05 個人パラメータと不確実性

**3つの概念を分けます。**

| 概念 | 定義 | 意味 |
| --- | --- | --- |
| A. 範囲の中の位置 | z = (E′ − μ) / h | 範囲の端が ±1。確率でも信頼性でもない。μ・h が不確かなので、z にも 95% 区間を付ける |
| B. 回答そのもののばらつき | E_θ[Var(Y │ x, θ)] | θ が分かっていても残る、答えの散らばり |
| C. 推定の不確かさ | Var_θ[E(Y │ x, θ)] | 記録から、その人をどこまで絞り込めたか |

B ＋ C ＝ Var(Y │ x, D)（全分散の法則）です。気象入力の誤差とモデルの構造の誤りは、この2項には入りません。

**予測分布**：

```
P(Y = k │ x, D) = Σ_m w_m(x) ∫ P(Y = k │ x, θ, m) p(θ │ D, m) dθ
```

- p(θ │ D, m) は、ラプラス近似の正規分布 N(θ̂, H⁻¹) で近似します。記録がないときは、事前分布 N(μ₀, diag(σ₀²)) を使います。
- 積分は、モデルごとに 200 通りのパラメータを引いて平均します（乱数のシードは時刻の分で決まり、同じ分なら同じ結果）。
- w_m(x) は、モデルの事後確率（証拠による）を、入力のそろわないモデルを除いて正規化したもの（MATH-03）。
- **事前分布**：固定の値から始めます（中心 18℃±4、h 3℃、g 4℃、慣れの傾き 0.33）。これは**計算のための弱い事前分布**です。
  - 個人の快適温度を決め打ちしたものではありません（決定 D2）。
  - 肌感の表示の境目からは作りません。
  - 記録がないうちは、予測が自然に広がります。画面では、中心の温度を「学習結果」として示しません（MATH-07）。
- **α（慣れの速さ）**：記録が30件以上あるとき、M2 の証拠で格子 {0.6, 0.7, 0.8, 0.85, 0.9, 0.95} から選びます。この件数の条件は暫定で、#35 で見直します。
- **続けて記録したものの重み**（#62、comfort-4）：尤度の各項に重み w_i を掛けます（Σ w_i log P(y_i │ x_i, θ)）。同じ人の記録が前の記録から BURST_GAP_H = 2 時間以内なら同じまとまりとし、k 件のまとまりの各記録を w = 1 / (1 + (k − 1)ρ)、ρ = 0.5 とします（k 件を、相関 ρ の k 件の有効件数として数える）。合成データ（`bursts.ts`）で、重みなしでは μ の被覆率が 69〜91% に落ちるのに対し、ρ = 0.5 で 89〜98%、誤差と予測の RPS もすべての条件で改善しました。ρ = 1（まとまりを1件分）は区間が広すぎます（被覆率 99〜100%）。1件ずつ記録する人には影響しません。
- **まとまりの長さの上限**（comfort-5、#86）：まとまりは、最初の記録から BURST_MAX_SPAN_H = 3 時間で区切ります。間隔だけで決めると、1.5〜2時間おきに1日中記録する人は1日が1つのまとまりになり、場面の違う記録まで少なく数えていました（合成データ `burst-cap-results.md`：約40件で区間の幅 3.5℃ → 2.2℃、被覆率 100% → 92%、予測の RPS 0.0420 → 0.0436。続けて記録する人・1件ずつ記録する人では変化なし）。選好モデル（MATH-09）と時間帯の件数（MATH-07）の重みも同じ決まりです。
  - 限界：まとまりを越えて続く個人のずれ（その日の調子など）は扱っていません。comfort-4 は「前の記録との間隔」だけでまとまりを決めるので長さに上限がなく、1.9時間おきに続けると半日分が1つのまとまりになっていました（レビュー 2026-11-12）。comfort-5 の上限3時間はこれを直す一方、その人の予測の RPS は少しだけ悪くなります（約40件で 0.0420 → 0.0436、約120件で 0.0399 → 0.0402）。区間が正直になる（被覆率 100% → 92〜95%）ことと引き換えです。ρ・間隔・上限は合成データで選んだもので、実データの時系列評価で見直します。
- **実装**：`src/beta/engine/estimation.ts`（`fitModel`、ラプラス近似、`interval`、重み付きの `negLogJoint`）、`observations.ts`（`burstWeights`、`BURST_GAP_H`、`BURST_RHO`、`BURST_MAX_SPAN_H`、版ごとの読み方 `ObsSettings`）、`model.ts`（`PRIOR`、`priorFor`）、`ensemble.ts`（`fitEnsemble`、`ensembleFromReports`）、`prediction.ts`（`drawsOf`、`predictComfort`、`muIntervalOf`）
- **検証（#35）**：ラプラス近似の μ の区間は、重点サンプリングによる区間より、5〜40件で平均 4〜8% 狭いだけでした。被覆率も 91〜100% だったので、補正は入れていません。
- **状態**：定義済み・実装済み・合成データで検証済み

## MATH-06 予測と学習の時間順序

1. 回答前の気象を確定する：スナップショット（MATH-02）を、取得時刻・版と一緒に固める。
2. 事前予測を保存する：送信した時点で計算し直し、次のものを記録に入れる。
   - 7段の確率
   - 位置・区間・ばらつき
   - 学習の段階
   - モデルごとの予測
   - 予測の版
3. 回答を取る：予測とは別の観測事実として保存する（予測は回答を使わない。表示は回答を選んだ後だけ）。
4. 誤差を評価する：保存してある事前予測と回答を比べる（MATH-08）。
5. 学習データを更新する：品質の条件（MATH-02）を満たす記録で、推定し直す。
6. 新しい予測：次の記録から、新しい推定で予測する。

**禁止**：回答の後に学習し直したモデルの確率で、回答前の予測を上書きしてはいけません。

**再解析との区別**：
- 当時の予測の評価は、記録に残した事前予測だけで行います。
- 後日、速報値が確定値に置き換わった後で推定し直すことはあり得ます（再解析）。ただし、その結果は当時の成績とは別のものとして扱い、同じ記録に混ぜません。

- **実装**：`src/beta/ReportSheet.tsx`（送信時に計算し直す）、`trackRecord`／`modelRecords`（保存した予測だけを使う）
- **状態**：定義済み・実装済み

## MATH-07 推定できるかどうか（学習の段階）

件数ではなく、識別に必要な条件で決めます（決定 D8）。

| 段階 | 条件 | 画面 |
| --- | --- | --- |
| 未学習 | 学習に使える記録が0件 | 答えの分布だけ（初期値による参考）。中心の温度は出さない |
| 情報不足 | 寒い側と暑い側の両方の答えがない／E′ の幅が5℃未満／記録した日が3日未満 | 足りないものを示す。中心は「未特定」 |
| 暫定 | μ の 95% 区間（最新の記録の条件で）が4℃より広い／3件分以上ある時間帯が2つ未満 | 区間つきで示す |
| 検証可能 | 区間が4℃以内で、学習に使う記録が3件分以上ある時間帯（朝・日中と昼・夕方・夜。太陽の高さで区切る、下の「時間区分」）が2つ以上 | 事前予測の検証を始める |
| 検証済み | 検証可能の間に出した事前予測が20件以上あり、その平均 RPS が基準（MATH-08）より小さい | — |

- 境目（5℃、3日、4℃、20件）は、#35 の合成データの検証で根拠を確かめました（[README.md](README.md) の表）。μ の区間 4℃ は、理想的な場合には緩めてもよい結果でしたが、実データのずれを見込んで保守的なままにしています。
- 同じ日の連続した回答は、独立な観測として数えすぎないよう、日数を条件にし、尤度でも重みを下げます（MATH-05、#62）。
- **時間帯の偏り**（#62）：1つの時間帯だけで学んだ中心には、その時間帯の服装・活動が混ざります。重みで均すと少ない時間帯の数件が効きすぎるので、均さずに、検証可能へ進む条件に時間帯の広がりを加え、記録の少ない時間帯の予測には注記します（`TIME_BANDS`、`bandCounts`）。
- **時間区分**（D16、#91）：朝・日中・昼・夕方・夜は時計ではなく**太陽の高さ**で区切ります（`shared/dayParts.ts`）。夜＝太陽が地平線の下6°より低い（市民薄明の外）、朝＝そこから南中高度の半分まで、日中＝南中まで、昼＝南中から南中高度の半分まで、夕方＝そこから地平線の下6°まで。固定の角度でなく、その日の南中高度の半分にするのは、高知の南中高度が冬33°・夏80°と違い、固定の角度では冬の昼がほとんどなくなるためです。学習の時間帯は、朝・「日中と昼」・夕方・夜（夜は暗い時間すべて）の4つです。画面の時間帯（肌感の値、時間帯のグラフ、肌感マップ）も同じ区切りで、値の帯としての夜は夕暮れから3時間です。
  - 太陽の高さ（物理量）と、「朝らしさ」（服装・活動）や「暑さへの効き方」（モデル）は**別のもの**として扱います。時間区分は、場面を分けて数えるための**決まり**で、モデルの入力ではありません。暑さに効く日射は観測した日射量（日なた温度、MATH-03）、夜の余熱・前夜の冷え込みは日の入り〜日の出（D15）で扱います。時間区分そのものが答えのずれを説明するか（服装や活動の違い）は、別のモデルとして、実データで比べて確かめます。
  - 太陽の計算（NOAA の太陽位置の式、`shared/sunTimes.ts`）は、国立天文台の高知の表（2026年3・6・10月）と比べて、日の出・日の入り・南中の MAE 0.24〜0.27分（表の丸め ±0.5分と同程度）、南中高度の MAE 0.02°。別の実装 SunCalc とも比べ、境目の前後5分を1分刻みで判定して食い違いを数えました（`research/sun/verify-results.md`）。SunCalc は国立天文台に対しておよそ1.3分遅れるため、正しさの基準には国立天文台を使います。
- 説明変数どうしの強い相関（例：風と気温）がある場合、効果を分けて推定できません。推定の相関が |r| ≥ 0.9 の組を「分けられない組」として検出し、根拠の画面に出します（`confoundedPairs`）。
- **実装**：`src/beta/engine/learning.ts`（`learningOf`、`learningFrom`、`LEARNING_RULES`、`centreUnknown`、`TIME_BANDS`、`bandCounts`）、`shared/dayParts.ts`（`dayParts`、`partAt`）、`shared/sunTimes.ts`、`estimation.ts`（`confoundedPairs`）
- **状態**：定義済み・実装済み・境目は合成データで確認済み（実データで見直す）

## MATH-08 予測の評価とモデル選択

| 指標 | 定義 | 役割 |
| --- | --- | --- |
| RPS（主指標） | (1/6) Σ_{k=1}^{6} (F_k − O_k)²。F は予測の累積確率、O は回答の累積（0/1）。**6で割る** | 順序を考えた確率予測の評価。0 が最良、1 が最悪 |
| 対数損失（補助） | −log P(Y = y) | 回答にとても低い確率を付けていないか。log 7 ≈ 1.95 が当てずっぽう |
| 較正 | 予測確率の区間ごとの実測頻度 | 70% と予測したことが約70%起きるか（#34） |
| 予測の分散・エントロピー | MATH-05 の B と C | 同じ条件でどれだけ答えが散らばるか |
| 時系列の外部評価 | 回答前に出した予測だけで、学習が進むにつれての成績 | 学習で予測が良くなっているか（#34） |

- **基準モデル**：その人のそれまでの答えの割合（各段に1を足して平滑化）。初期の快適温度を仮定した基準は使いません。
- **モデル選択**：重みは証拠（ラプラス近似の周辺尤度）で決めます。ただし「複雑なモデルの方が良い」と判断するのは、回答前に出した予測の成績が良くなったときだけです（#34）。
- **実装**：`src/beta/engine/evaluation.ts`（`rps`、`referenceProbs`、`trackRecord`、`modelRecords`）。アプリ内の研究用の分析（`src/research/analysis.ts`、#79）で、全員分を集計する：
  - 件数で平均と、人ごとに平均の両方（#62 C。よく記録する人に引っ張られないか）。
  - 予測の版ごとの成績（送信時の予測。版ごとに期間が違うので参考）。
  - **7段の較正**：6つの累積確率 P(Y ≤ k) の予測と実際（決定 D14）。保存された確率は丸めてあるので、合計で割り直してから使う。
  - comfort-3 と comfort-4 を同じ記録で比べる計算（最近10件を、それより前の記録だけで2通りに学び直す）。予測される側は学習に使える記録だけ（入力が予報・古い記録は除く）、基準（それまでの答えの割合）はそれより前のすべての答え。成績の表（`trackRecord`）と同じ母集団ではない（あちらは送信時に予測のあった記録すべて）ので、両者の数字を直接比べない。
  - 選好モデルの時系列評価（MATH-09）。
- **成績の決まり**（`trackRecord`・`modelRecords`）
  - 評価するのは、送信した時点で記録に残した予測だけ（MATH-06）。
  - 尺度の版が今のもの（3）である答えだけを使い、それ以外の件数は別に示す（MATH-01）。
  - スキル = 1 − RPS ／ 基準の RPS。0より大きければ、基準より当たっている。
  - 較正：1つの予測から、寒い側・ちょうどよい・暑い側の3つの確率を取り出し、区間ごとに、予測の平均と実際に起きた割合を並べる。区間は 0–0.1、0.1–0.3、0.3–0.5、0.5–0.7、0.7–0.9、0.9–1。
  - 時系列：時刻の順に10件ずつ、RPS と基準を並べる。
  - 変化の目印：直近10件の（答え − 期待値）の平均の絶対値が 0.5段を超えたら、「感じ方が変わったかもしれない」と知らせる。#35 では、+3℃ の変化を 10/10 で検出し、変わらない人での誤検出は 0/10 だった。
- **状態**：実装済み（#34）。境目（10件・0.5段）は、合成データで確認した値で、実データで見直す。

## MATH-09 温熱選好・飲料温度選好（#63）

温冷感（MATH-01〜08）とは別の2つの観測です。温冷感のモデル（comfort-4）は変えません。

- **観測**：温熱選好 P_t ∈ {−1, 0, +1}（涼しくしたい／このままでよい／暖かくしたい）、飲料温度選好 B_t ∈ {−1, 0, +1}（冷たい／どちらでもよい／温かい）。符号は D13。任意回答で、未回答は観測なし（0 ではない）。`preferenceVersion` のない記録は、問いが出る前のもの。
- **指数**：I_P(t) = P(P_t = +1) − P(P_t = −1)、I_B(t) = P(B_t = +1) − P(B_t = −1)。範囲は −1〜+1、正は暖かい方向。0 は「現状維持」とは限らないので、3つの確率を併記する。3つの尺度は別の構成概念で、同じ値でも同じ意味とは限らない。
- **モデル（P3 #66 の候補）**：個人ごとの正則化した多項ロジスティック（3カテゴリ）。P(B_t = b │ x_t, θ) ∝ exp(α_b + β_bᵀ x_t)。温熱選好も独立に。
  - **2つの予測を分ける**：回答前の予測（気象と過去の回答だけ）と、同時点の温冷感 Y_t を使う予測。前者の成績として後者を報告しない。
  - 続けて記録したものの重み（MATH-05、#62）を同じように使う。
  - 時間の重み（半減期）は、一定の重みと複数の候補を、将来の回答の予測成績で比べる。決め打ちしない。
- **学習・評価と表示の開始は別々に判定する**。どちらも期間ではなく、有効回答数（重みを使った数）、カテゴリの偏り、気象条件の広がり、予測の不確実性で決める。境目は合成データ（P5 #68）で決める。
- **評価**：RPS（3カテゴリ）と対数損失、較正。時系列で分けた事前予測だけで。
- **実装**：`src/beta/preference.ts`（符号の変換と指数）、`src/beta/preferenceModel.ts`（`fitPreference`・`predictPreference`・`preferenceLearning`・`PREF_RULES`・`preferenceObservations`）。入力は標準化した (E′ − 20)/5、(a − 15)/5（と Y/3）、係数の事前分布は N(0, 1.5²)、不確かさはラプラス近似と200通りの引き直し。
- **合成データの検証**（`preference-synth.ts` → `preference-synth-results.md`、各100人）：指数の95%区間の被覆率 91〜96%。表示の条件（重み付き20件分以上・2種類以上の答え・温度の幅5℃以上・区間の幅0.8以下）を満たすのは20件で74%・80件で93%、満たしたときの誤差は0.09〜0.18。天気と関係のない人では区間が0を含む（94〜100%）ので、表示するときは「はっきりした傾きなし」と示す必要がある（P4）。温冷感を使う予測は、この仮想の人では回答前の予測と差がない（温冷感も気温から作ったため。実データで改めて比べる）。半減期30日は、変わる人で RPS 0.124 → 0.119、変わらない人で 0.127 → 0.128 と差が小さく、今は使わない（`PREF_DEFAULT`）。
- **表示（P4）**：根拠の画面の「この日の選好」。条件（`PREF_RULES`）を満たすまでは答えの件数と足りないものだけ。満たしたら、その日の日中の日なた温度と最近の基準での指数・95%区間・3つの確率。区間が0を含むときは「はっきりした傾きはありません」と言葉で示す。21日より前の答えだけで学んだ自分と比べ、差が0.2以上なら言葉で示す。今日の分は、その日最初の記録まで隠す。
- **状態**：実装済み・合成データで検証済み・根拠の画面に表示（β・試験中）。境目と半減期は実データで見直す
