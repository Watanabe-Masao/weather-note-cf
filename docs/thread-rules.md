# スレッドの分担と運用ルール

メインのスレッド（「天気アプリ」）が管理する。作業スレッドは書き換えない。

## 今の形（2026-11-17 から）
- **作業はメインに集める。** 画面・サーバーの作業はメインのスレッドで行う。
- **別のスレッドを使うのは「調査」だけ。** 調べものは、コードに触らず research/ と research/* ブランチだけで完結し、ほかの作業とぶつからないため。調査のスレッドは「調査」の名前で1つだけ使い、次の調べものも同じスレッドに送る（長くなったらメインが開き直しを頼む）。
- 指示書の1行目に宛先（例：「宛先：調査」）を書く。

### 分けてみて分かったこと（2026-11-17）
- 作業ごとにスレッドを開くと数が増え（1日で6つ）、名前・役割が追いにくくなった。
- 指示書は人の手で貼るので、貼り間違いで同じ作業が2つのスレッドで動き、同じ直しを2回作った（#260、無駄な手戻り）。
- うまくいったこと：PR のコメントでの報告とレビュー、担当範囲で触るファイルを分けること、迷ったら止まって報告すること、最後の返事の形。これらは調査のスレッドでも続ける。
- 作業を始めるときは、PR のブランチの最新の積み込みと PR のコメントを見て、ほかで作業していないか確かめ、PR に「着手しました（スレッド名）」と書く。

以下は、別のスレッドで作業するときの決まり（今は調査のスレッドに当てはまる）。

## スレッドの役割
- **メイン（「天気アプリ」）**：渡辺さんとのやり取りはここだけ。レビュー、工程管理、指示書づくり、要件定義書の更新、渡辺さんの OK を受けてのマージ。
- **作業スレッド**：1つの作業（PR 1つ分）を始めから終わりまで行う。渡辺さんが開き、メインが書いた指示書を貼る。マージしたら終わり。
- 続けて覚えておくことは、スレッドではなく、docs/・要件定義書・PR に残す。

## 担当範囲（同じファイルを2つのスレッドが触らない）
| 範囲 | 主なファイル |
|---|---|
| サーバーとデータ | worker/、shared/ の予報・監視・取り込み、scripts/health-check.mjs、.github/workflows/health.yml |
| 画面とデザイン | src/、docs/design-system.md、test/ui/、e2e/ |
| 調査 | research/、research/* ブランチ |

指示書に「変更してよいファイル」を書く。そこにないファイルは触らない。関係するテストは触ってよいが、報告に書く。重なりそうなら止まって PR のコメントに書く。

## 作業の流れ
1. main からブランチを作り、下書き（draft）の PR を出す。
2. 報告は **PR のコメント** に「今回対応／記録して保留／まだ判断できない」の形で書く。
3. メインが PR を読んでレビューし、直してほしい所を PR のコメントに書く。
4. 渡辺さんが作業スレッドに「PR #番号 のコメントを見て続けて」と送ったら、直して同じ PR に積む。
5. マージはメインが渡辺さんの OK のあとに行う。作業スレッドはマージしない。

## 作業スレッドの最後の返事（毎回この形だけ）
手を止めるとき（PR を出した・直しを積んだ・判断待ちで止まった）は、チャットの最後の返事を次の形の1つの枠だけにする。渡辺さんがそのままメインに貼る。中身の説明はチャットに書かず、PR のコメントに書く。

```
【メインへ】<スレッド名>：<済／判断待ち／つまずき> PR #<番号>
<一言（何をしたか、または何を決めてほしいか）>
```

- 「判断待ち」は、決めてほしいことを PR のコメントに書いたうえで出す。
- 「つまずき」は、権限・環境などで進めないとき。理由を PR のコメント（PR がなければ一言の中）に書く。

## いつも守ること
- **Watanabe-Masao/weather-note（-cf のない方）には push しない。** 作業は weather-note-cf だけ。
- 秘密の鍵はチャットにもリポジトリにも書かない。メールアドレスやアプリの URL を、リポジトリ・issue・PR・Actions の出力に書かない（このリポジトリは公開）。
- 新しいライブラリ、モデルの採用・変更は、先に渡辺さんの OK。
- 消すなど元に戻せない操作は、1つずつ確認してから。
- 外部のサイトは利用条件と robots.txt を先に確かめ、禁止された範囲は確認のためでも読まない。読めないときは「確かめられなかった」と報告する（#267）。
- 公開の場所（PR・issue・Actions の出力）に、外部の仕組み（ビルドの通知など）が URL などを自動で書き込んでいたら、消さずに報告する。
- 取れなかったものを「ない」と見せない（「確かめられなかった」と「無い」を分ける）。
- 「仕組みができた」と「結論が出た」を分けて書く。
- UI は作る前に見本（触れるサンプル）で確かめる。
- 迷ったら勝手に決めず、PR のコメントに書いて止まる。
- 既存の決まりから導けることは先に作って PR で確かめてよい。新しい判断は報告して待つ。
- 知らせ（毎時の見張り・毎朝の点検・監視の issue）や、いつもと違うことは、メインのスレッドが `docs/runbook.md`（障害とイレギュラーの手引き）の手順で受ける。S1（取り戻せる期限があるもの）は、ほかの作業より先にする。「処理が抜けた」と「データが欠けた」を分けて記録する。
- 新しい知らせを足すときは、`shared/runbook.ts` と手引きに手順を足す（足し忘れは `test/runbook.test.ts` が落とす）。
